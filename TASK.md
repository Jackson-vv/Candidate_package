# Тестовое задание для Data Engineer: мини-DWH продаж и планов

## Контекст

Есть продажи из 1С, план продаж из Excel и справочник связей номенклатуры.  
Нужно построить ежедневную витрину план/факт, которую можно использовать в BI.

Период данных: январь–март 2025 и январь–март 2026.  
В данных есть 12 продуктов и 4 торговые цепочки.

## Цель

Сделать мини-DWH на одном из вариантов:

- Python + SQL + DuckDB
- Python + SQL + SQLite
- Python + SQL + PostgreSQL

Рекомендуемый вариант для простоты — DuckDB.

## Исходные файлы

Файлы лежат в папке `data/`:

- `sales_1c.csv` — продажи из 1С
- `plan.csv` — месячный план продаж
- `sku_links.csv` — связи старой и актуальной номенклатуры
- `product_catalog_optional.csv` — справочник товаров, можно использовать по желанию
- `stock_movements_optional.csv` — данные для задания со звездочкой

## Что нужно сделать

### 1. Загрузить данные в raw-слой

Создать raw-таблицы:

- `raw_sales_1c`
- `raw_plan`
- `raw_sku_links`

Raw-слой должен хранить данные максимально близко к исходным файлам.

### 2. Сделать staging-слой

Создать staging-таблицы:

- `stg_sales`
- `stg_plan`
- `stg_sku_links`

В staging нужно:

- привести даты к типу date;
- привести числовые поля к numeric/decimal/float;
- убрать лишние пробелы в строковых полях;
- обработать пустые значения;
- не удалять отрицательные продажи.

Отрицательные продажи могут быть возвратами. Их нельзя автоматически считать ошибкой.

### 3. Обработать связи номенклатуры

Если в продажах есть старая номенклатура `old_sku_id`, ее нужно заменить на актуальную `current_sku_id` из `sku_links.csv`.

Пример:

```text
SKU_OLD_001 -> SKU_001
```

В итоговой витрине старая номенклатура не должна оставаться как аналитический идентификатор товара.

### 4. Найти дубли документов

В файле продаж есть намеренно добавленные дубли по `doc_id`.

Нужно:

- найти дубли;
- вывести их в лог или отдельную таблицу/файл;
- в README описать, что вы делаете с дублями при построении витрины.

Допустимые варианты:

- пайплайн падает на проверке качества;
- дубли исключаются из витрины;
- дубли попадают в quarantine/error table.

Главное — решение должно быть осознанным и описанным.

### 5. Распределить месячный план по дням

В `plan.csv` план задан на месяц по цепочке, региону и товарной группе.

Поля весов:

- `mon_weight`
- `tue_weight`
- `wed_weight`
- `thu_weight`
- `fri_weight`
- `sat_weight`
- `sun_weight`

Нужно распределить месячный план по дням месяца пропорционально весам дней недели.

Обязательная проверка:

```text
сумма дневного плана за месяц = месячный plan_qty
```

### 6. Построить итоговую витрину

Создать таблицу:

```text
mart_sales_plan_daily
```

Поля:

```text
date
region
chain_id
chain_name
product_group
actual_qty
plan_qty
delta
completion_pct
```

Где:

```text
actual_qty      = факт продаж за день
plan_qty        = план продаж за день
delta           = actual_qty - plan_qty
completion_pct  = actual_qty / plan_qty * 100
```

Если факт есть, а плана нет — строка должна быть.  
Если план есть, а факта нет — строка должна быть.

### 7. Проверки качества данных

Минимальный список проверок:

1. Найти дубли `doc_id`.
2. Проверить, что сумма дневного плана за месяц равна месячному плану.
3. Проверить, что старая номенклатура заменена на актуальную.
4. Проверить, что нет пустых `date`, `region`, `chain_id`, `product_group` в витрине.
5. Проверить, что повторный запуск не создает лишние дубли.

Проверки можно реализовать SQL-запросами, Python-кодом или отдельным скриптом.

### 8. Логирование

Скрипт должен писать простые логи:

- сколько строк загружено в raw;
- сколько дублей найдено;
- сколько строк в итоговой витрине;
- прошли ли проверки качества.

### 9. Повторный запуск

Решение должно корректно запускаться повторно.

При повторном запуске результат должен быть тем же, что после первого запуска.

## Задания со звездочкой

Необязательно, но будет плюсом.

### 1. Последняя операция клиента

Для каждого клиента выбрать последнюю продажу:

```text
customer_id
last_doc_id
last_date
last_sku_id
last_qty
last_revenue_byn
```

### 2. Rolling 7-day metric

Посчитать скользящую сумму продаж за последние 7 дней:

```text
date
region
chain_name
product_group
actual_qty
rolling_7d_actual_qty
```

### 3. Month-to-date metric

Посчитать накопительный факт с начала месяца:

```text
date
region
chain_name
product_group
actual_qty
mtd_actual_qty
```

### 4. Остаток на складе в BYN по дням

Используйте файл:

```text
stock_movements_optional.csv
```

Нужно посчитать:

```text
date
warehouse_id
warehouse_name
sku_id
stock_qty
stock_value_byn
```

Логика:

- `income` увеличивает остаток;
- `outcome` уменьшает остаток;
- остаток считается накопительно по дням;
- `stock_value_byn = stock_qty * unit_cost_byn`.
